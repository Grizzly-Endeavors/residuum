# Editing config.toml and providers.toml

Your own config lives in `config/config.toml` and `config/providers.toml` inside your workspace. Write them directly with `write_file`/`edit_file` when the user asks for a config change — both are writable. `config.example.toml` and `providers.example.toml` stay blocked: Residuum regenerates them from its own defaults on every startup, so any edit to them is lost at the next restart. Edit `config.toml`/`providers.toml` instead.

## Which file holds a setting

- `config/config.toml` — everything of yours except providers and models: `[agent]`, `[background]` (idle timeouts and depth cap), `[subconscious]`, `[memory]`, `[discord]`/`[telegram]`/`[teams]`, `[a2a]` (`visibility` only), `[web_search]`, `[tools]`, `[webhooks.<name>]`, top-level `timeout_secs`/`max_tokens`/`temperature`/`thinking`/`autostart`.
- `config/providers.toml` — provider credentials and `[models]` role assignments (`main`, `subconscious`, background tiers). A model that can't view images is marked under its provider entry: `[providers.zai.models."glm-5.3"]` with `input = ["text"]` (`["text", "image"]` for one that can). For such a model, images in messages and tool results are replaced in each request with `(image omitted: this model can't view images)`; the conversation keeps them. Unset, images are sent; if the provider refuses them and a retry without them is answered, that model gets none until Residuum restarts (declaring `["text", "image"]` undoes that on reload). In a failover chain, a request with images goes first to the hops that take them, and a hop that refuses images while a later one takes them is passed over silently and remembered as text-only. The user is told when a new image is left out.
- The hub's `hub/config.toml` — the timezone, `[gateway]`, `[cloud]`, the A2A listener (`[a2a]` `enabled`/`port`/`public_url`), `[tracing]`, `[push]` `contact` (the `mailto:` or `https:` contact Web Push services see), `[background]` `max_concurrent`/`hop_soft_limit`/`hop_hard_limit`, and `[pricing."provider/model"]` (per-model prices in USD per million tokens, keyed by the provider kind and model id, that override the built-in prices used for cost estimates; an entry with a bad key or a negative or non-finite rate is ignored with a notice, and a model with no price has no estimate; the Settings modal's Model prices section under All agents edits them). It sits outside your workspace at `~/.residuum/hub/config.toml`; edit it by that absolute path, the same way, and only when the user asks — these settings apply to the whole hub, not just you. The reload outcome arrives as a system note for it too.
- Workspace `config/*.json`/`*.toml` (`mcp.json`, `channels.toml`, `agent-card.json`, `a2a.json`) — per-system files, not global settings. Read the matching reference (mcp.md, notifications.md, a2a.md) before editing one of these; they have their own formats.

## Model settings in config.toml

- `timeout_secs` (default 120) — how long a model call may take. A reply that streams in fails only if nothing at all arrives for this long, so it never cuts off a long answer for its length; a stall reads "the model stopped responding for Ns".
- `[retry]` — retries apply to streamed replies too. A stream that fails partway (an overloaded provider, a dropped connection, a reply that ends early) is retried, and what had already streamed is discarded first so the retry never appends to it. A fallback provider does the same when it takes over.
- `max_tokens` — caps the output of each model call. A request that sets its own limit (the subconscious uses 1024) overrides it. Anthropic and Gemini take it as their own limit field, Ollama takes `num_predict`, OpenAI's own API (and Azure OpenAI) takes `max_completion_tokens`, and Fireworks takes `max_tokens`. Other OpenAI-compatible hosts get `max_tokens` only when a call sets a smaller limit (the subconscious's) and otherwise use their own default, because servers like vLLM refuse a request whose prompt plus limit exceeds the model's context. On OpenAI's own API the subconscious's calls also get `reasoning_effort: "low"` (dropped for a model that refuses it), so a reasoning model doesn't spend its 1024 tokens reasoning; a subconscious evaluation that still runs out with no answer fails with a `warn` instead of reading as no findings.
- Prompt caching — providers reuse work on a request whose start matches an earlier one byte for byte, so a change to your system prompt invalidates the cache from that section on, the conversation included. Its sections run from the rarely changing ones (`SOUL.md` through `TEAM`) to the ones that change with memory and skills (`OBSERVATION_LOG`, `RECENT_CONTEXT`, `SKILLS_INDEX`, `ACTIVE_SKILLS`). On Anthropic an explicit cache breakpoint sits after `TEAM`, so editing `SOUL.md`, team `AGENTS.md`, team `USER.md` or the wiki root index costs more than a new observation; there is also a top-level breakpoint for the rest of the request. A main-conversation turn a person started keeps its cache for an hour (writes cost 2x base input instead of 1.25x); everything else, sessions included, keeps it five minutes. Other providers get the same text and cache the longest matching prefix themselves; OpenAI's own API (`api.openai.com`) also gets a `prompt_cache_key` that keeps a conversation on one cache: `residuum-main-<hash of the workspace path>` for the main conversation, the run id for a session, none for the memory observer, reflector and subconscious. `cache_read_tokens` and `cache_creation_tokens` in usage show what was read and written.
- Cache break log — each main-conversation and session model request is compared with the conversation's previous one, and a change to a part already sent (the tools, the system prompt, an earlier message) is logged as `prompt cache prefix changed` with the `part`, the first differing `index`, the system-prompt `section` and a `cause`. Expected changes (the observer rotating history) log at `debug`; a tool added or removed, the system prompt or a tool's definition changing between turns log at `info`; an earlier message changing without a rotation, tools reordered, or the system prompt or a tool changing within one turn log at `warn`. Each `info` or `warn` cause logs at that level once per conversation, then at `debug`.
- `thinking` — `off`, `on`, `low`, `medium` or `high`; a model role's entry in `providers.toml` can override it (`observer = { model = "...", thinking = "off" }`). Anthropic gets adaptive thinking (`low`/`medium`/`high` set its effort), and a model that only takes a manual token budget is switched to one automatically (a quarter, half or three quarters of `max_tokens`, at least 1024 and below `max_tokens`; with `max_tokens` of 1024 or lower thinking is left off). OpenAI-compatible hosts get `reasoning_effort`, Gemini a thinking budget plus thought summaries, Ollama `think`. Reasoning comes back as a summary where the provider offers one; OpenAI's own Chat Completions API returns none. On GPT-5.4 and later, OpenAI's Chat Completions API refuses tools together with any thinking, so a turn on those models fails with a message saying to set `thinking = "off"` for that model or pick another.
- Reasoning from the tool-use exchange in progress is sent back with its tool calls where a provider needs it (Anthropic's signed blocks, Gemini's thought signatures, `reasoning_content` for DeepSeek-style hosts, `message.thinking` for Ollama). Anthropic also gets earlier turns' reasoning back unchanged, so the prompt cache holds through them; the other providers don't. Each Anthropic block records a fingerprint (`binding`) of the request that produced it, and an earlier turn's block goes back only while everything ahead of it (system prompt, tools, earlier messages) is unchanged; a change leaves it and every later block out, and reasoning written after the change goes back as usual. Only a reply's leading reasoning ever goes back: reasoning that came after a web search or other content in the same reply is shown but never sent back. Each provider sends back only reasoning it produced itself: every block records its provider and model as an `origin`, and reasoning another provider or model wrote (after a failover to a fallback, say) is left out of the request instead of failing on a signature the next provider can't verify. A block with no `origin` is never sent back. A Gemini 3 model that takes over a tool-use exchange another provider began is sent Google's documented stand-in signature, `skip_thought_signature_validator`, on the first function call of each step, because it refuses a function call with none. When an OpenAI-compatible host that gets reasoning back refuses a request for missing `reasoning_content` (DeepSeek in thinking mode does, for tool calls another provider made), the request is resent once with `reasoning_content` of `(reasoning for this step is not available)` on each tool-calling message of the exchange that has none of the host's own, and that client keeps doing so from then on; a host that never refuses never gets it. Current Claude models tie each reasoning block to the system prompt, tools and messages ahead of it; when the API refuses a replayed block as bound to a different conversation, the request is resent once with `thinking.block_binding.prefix_mismatch_behavior = "drop_block"` (beta header `thinking-binding-controls-2026-08-01`), that client keeps sending it from then on, and a turn in which the API reports dropping reasoning shows one notice saying so.

## How to edit

1. Use `edit_file` with a targeted `old_string`/`new_string` that changes only the lines that need to change — both files carry comments and commented-out examples the user relies on, and a full `write_file` rewrite drops them.
2. If the key doesn't exist yet, add it under the matching `[section]` header (adding the header itself if the section is absent), placed near related keys rather than appended at the end of the file.
3. Match the file's existing style: comment out an example you're leaving as a hint, uncomment and set a value to enable it.
4. If the field you're editing already holds a `secret:<name>` or `${ENV_VAR}` reference, keep that reference form — edit around it rather than replacing it with a plaintext value. When the user says a credential is already stored as a secret, ask for its name and write `secret:<name>`; don't ask the user to paste the plaintext value into the conversation when a stored reference will do.
5. After the write succeeds, a background watcher picks up the change and reloads automatically — there is no tool-level confirmation of this in `write_file`/`edit_file`'s own result. The reload's outcome ("configuration reloaded: ..." or "config reload failed: ...") is published to the user's interface (a notice in the web UI, chat, etc.) *and*, because this write is yours, arrives as a system note in your own transcript on your next step — you don't need to ask the user to check for you. Before writing, re-read the edited section to make sure the TOML is well-formed (balanced quotes/brackets/tables, correct value types) — a malformed file fails the reload and Residuum keeps running on the previous config until it's fixed.
6. Tell the user what changed — name the section, the key, and the new value, not just "updated the config". Once the system note confirming the reload arrives, mention its outcome too rather than assuming success; if it reports a failure, say so and offer to fix it.
