# Workspace split, round 2: the bus, the runtime, the hub and the gateway as their own crates

**Status:** design, not built. D1-D14 in §2 are decided. Round 1, whose shape and rules this builds on, is in [`docs/archive/workspace-split.md`](../archive/workspace-split.md); the layout it produced is the [Workspace layout](../../CONTRIBUTING.md#workspace-layout) section of `CONTRIBUTING.md`.

## 1. Summary

After round 1 the root package `residuum` still holds about 186k lines (343 files under `src/`), and a one-file edit there rebuilds all of it: about 13.5s for `cargo build` and about 19s for `cargo test --no-run` and clippy, of which 64% is the root crate's front end and 7-9% is linking. The lever is the size of the crate an edit lands in and of the crates above it, so round 2 moves everything between the lower crates and the binary into thirteen new member crates and leaves the root as the binary, the CLI and the wiring.

## 2. Decisions

Each decision below changes how the code is laid out for every future change. D1-D14 are decided; each records the choice, what it costs, and in a line or two why the alternatives lost. Some background the decisions rely on:

- **Where checks run today.** Three places check a change before it reaches `main`. The pre-push hook (on the developer's machine, before each push) runs clippy and the tests of the code the push touches. The pull request lane runs only two early warnings that never block: the Windows clippy and, for web changes, the visual comparisons. The merge queue runs the full suite on each batch of queued pull requests merged onto `main`; that is the first and only place every test runs, and a failure there ejects the pull request from the queue and costs the batch a full run.
- **The rebuild model** behind the numbers. Of the 1,499 non-merge commits from 2026-09-16 to 2026-10-16, it takes the 671 that touch at least one Rust file under `src/` or `crates/` and at most 40 Rust files. For each Rust file such a commit touches, the crate holding the file and every crate that depends on it rebuild. "Critical path" is the longest dependency chain among the rebuilt crates, summed in lines, because a crate waits for the one below it; it is a proxy for wall time, since profiling after round 1 put most of a rebuild in the front end, which scales with lines. "Small edits" are file edits that rebuild at most 60k lines in all. The model assigns whole files to crates (its per-crate lines are §4's table) and ignores linking and per-crate overhead, which §12 measures. The cross-crate integration tests that move to `tests/it` count as one more target above the root, which every edit rebuilds when tests build.
- **How the model assigns files.** Each file goes to the crate §4 gives it: the runtime as four crates (D6); the hub-level, repair and file routes (the Teams setup routes among them) and `file_server` in the hub (D2); the Teams app setup in interfaces (D14); the inbox in workspace; whole files that move down in their new crate (`background/events.rs`, `interfaces/types.rs`, `interfaces/conversations.rs`, `agent/interrupt.rs` and `gateway/helpers.rs` in the bus, `process.rs` in core, `notify/types.rs` in config, `client_context.rs` in tracing-service); the A2A listener in a2a (D13); `gateway/startup/tools.rs` in tools (§5); and the tests that move to `tests/it` (D9) there. The same assignment with one runtime crate and `gateway::web` whole in the gateway scores 113k and 31%. The model is a script outside the repository that applies this method to the commit log; its figures guide the layout, and F2's measurements (§12) are the result.

### D1. Which way the hub and the gateway stack, and how their cycle breaks

**Decided: (a), the gateway on top.** The hub (the process: hosting agents, the hub HTTP app, push, the team) defines one trait, `AgentLauncher`, with one method, `start` (start an agent; return its control handles and its event loop), and the gateway implements it as `GatewayLauncher`; the root's `wiring` hands the gateway's launcher to `run_hub`. What else crosses is plain data the hub defines (`AgentControl`, `AgentStartInputs`, `AgentCleanup`, `StartedAgent`). With D2 (b) the hub builds every router it serves itself, so the repair and file routers need no trait method, and `HubWebRoutes` is not needed: the web app's files reach the hub as a function pointer in `HubInputs` (D8).

- **Costs.** The hub's tests that run real agents cannot stay in the hub crate, since the hub cannot depend on the gateway even for tests: the host's integration tests (`src/hub/host/tests.rs` and `src/hub/host/tests/`, 6.7k lines and 125 tests) and the 11 tests of `src/hub/runtime.rs`'s test module that start the whole hub through its `RunningHub` fixture (`:1079-1765`; they wait for a running agent's `/api/status` and read its A2A card). They become cross-crate integration tests in `tests/it` (D9). They reach hub items that are private or `pub(crate)` today (§6 lists them), and their `use super::*` becomes explicit imports. The hub's HTTP tests stay in the hub: their harness builds its repair and file routers from the hub's own builders (D2), and its running agents' routers are a fixture, not gateway code.
- **Rejected.** (b) the hub on top, with the services it gives agents moved below the gateway: two hub crates along a line kept clean by hand, and every gateway edit rebuilds the hub. (c) one crate for both (69k lines): every edit to either rebuilds both, 113k on the critical path.
- **What follows.** `AgentHost::new` and `HubRuntime::start` take the launcher; the 136 real-agent tests above move to `tests/it` and become the hub's slowest dependents, run by every hub and gateway push (D9).

### D2. Where `gateway::web` goes, and whether it splits into hub-level and agent-level routes

**Decided: (b), every route the hub serves moves into the hub; the process-versus-agent boundary is the crate boundary.** `src/gateway/web/` (20k lines, 27 files, 159 commits, the hottest directory) holds three kinds of route: the process-level routes the hub mounts once (hub config, secrets and keys, cloud and sign-in, update and shutdown, tracing, hub and team checkpoints, team files and the workbench, the static web app), the per-agent repair and file routes the hub mounts whether or not the agent runs, and the running agent's routes (sessions, scheduled, memory, model, the A2A status routes, `/api/status`, `/api/agent-inbox`), which the gateway's event loop mounts. The first two kinds move into the hub as `hub::web` (about 15k lines with their tests), with `gateway/file_server.rs` as `hub::file_server`; the gateway keeps the third. Four files serve two kinds and are split along the line first (`web/mod.rs`, `web/config.rs`, `web/a2a.rs`, `web/inbox.rs`). The shared state goes with the routes that own it: `ConfigApiState`, `WorkspaceScope`, `HubApiState`, `HubDir`, the workspace file API (used by the agent's repair routes and the team scope), `AgentFilesState`, `CheckpointAccess` and `FileRegistry` are the hub's, and the gateway builds the running agent's instances of them from the hub's types, as it does today. §5 has the split file by file.

- **Costs.** The busiest files are split once, and an edit to a file route, which the running agent mounts as well (`/api/a2a/agents/raw`, the inbox, chat history), lands in the hub and rebuilds the gateway with it. By the model the choice costs 2k on the critical path (96k against 94k under (a)) and makes 2 points more of the edits small: the gateway shrinks by 15k lines, so tools edits (73k under (a), 57k under (b)) cross under 60k and the gateway's own edits get cheaper (57k to 41k), while the hub-level web edits, now in the hub, rebuild 87k instead of 57k. The Teams setup routes, a repair route, come with them and call the Teams app setup in interfaces, so the hub depends on interfaces (D14) and an interfaces edit rebuilds 103k instead of 72k.
- **Rejected.** (a) keep `web` whole in the gateway and hand the hub its routes through `HubWebRoutes` and two launcher methods: the hub would serve code it cannot build or test alone.
- **What follows.** The hub serves the embedded web app, so the assets reach it through a getter of the hub's own type (D8), and its 29 asset-handler tests run on a fixture getter; the repair routes' log lines become `residuum_hub::web` targets, which the log-field test still checks as agent lines (§8).

### D3. Where the wire types live (`ServerMessage` and the other ts-exported protocol types)

**Decided: (a), a `residuum-protocol` crate** on bus and workspace, holding `gateway/protocol.rs` and the frame conversions the hub needs (`session_event_to_server_message`, `summary_from_live`, `workspace_frame`). `ServerMessage` (1.7k lines with its siblings, 18 `#[derive(TS)]` types) is used by the gateway, by the hub (`HubEvent::SessionFrame`, `src/hub/types.rs:14,432`; the hub WebSocket, `src/hub/http/ws.rs:39,47`; the session relay, `src/hub/http/session_relay.rs:21`) and by the WebSocket subscriber; once the bus carries the payload types (D7), `protocol.rs` depends only on bus and inference types in production.

- **Rejected.** (b) inside the hub crate: the agent's WebSocket protocol would be the hub's. (c) inside the bus: each of the protocol's 33 monthly commits would rebuild everything.

### D4. How the interfaces↔gateway cycle breaks, and whether the chat adapters become their own crates

**Decided: cycle (a), adapters (a).** `interfaces` references the gateway 44 times in production; the gateway constructs every adapter (`src/gateway/event_loop/http.rs:159-227`, `src/gateway/reload.rs:939-996`) and is edited four times as often, so the interfaces go below it. The control channel types and notice helpers move into the bus, `AdapterSenders` into `interfaces`, `stop_session` into `background` (returning its own error, whose messages the gateway and the `/stop` command show unchanged), and the WebSocket subscriber into the gateway (it is the gateway's WebSocket fan-out, and nothing else uses it). The Teams setup types, which `interfaces/teams/setup_types.rs` re-exports from `gateway::web::teams_setup::types` today, move into `interfaces::teams::setup_types`, beside the setup machinery that uses them (D14). The adapters stay one `residuum-interfaces` crate.

- **Rejected.** For the cycle, (b) the interfaces above the gateway behind an adapter-factory trait: the less edited code on top. For the adapters, (b) a core crate plus `residuum-teams`, `residuum-discord`, `residuum-telegram`: 94k on the critical path against 96k, and 35% small edits against 33%, because the hub would depend on the Teams crate alone, so Discord and Telegram edits would not rebuild it; three more crates for 2k, so an adapter is split out when a measurement shows its cost (§12 row 3e measures an interfaces edit).

### D5. Where `TeamLink`, the agent directory and the agent-facing slice of `hub::types` go

**Decided: (a), the team slice moves into the runtime as a `team` module, which sits in `residuum-background` (D6).** The router, `TeamLink`, `TeamTarget`, `parse_team_address`, the lifecycle types (`AgentSummary`, `AgentState`, `LifecycleError`, `Actor`, `CreateAgentRequest`, `A2aVisibility`, `DeleteOutcome`, `AgentLastError`, `AgentErrorKind`), `DirectoryHandle`, and a new `TeamDirectory` trait with the five methods the runtime calls (`list`, `summary`, `agent_a2a_router`, `create`, `delete`). The hub's `AgentDirectory` becomes `AgentDirectory: TeamDirectory` and adds the routers, lifecycle and events; `DirectoryHandle` holds a `Weak<dyn TeamDirectory>`. The team router delivers through the background messenger (`src/hub/team.rs:20-21` names `AgentMessenger`, and `background::messaging` names `TeamLink`), so the module has to be in background's crate. The ts-exported lifecycle types change path (`residuum::background::team::AgentSummary`), not content.

- **Rejected.** (b) keep `hub::team` in the hub behind a trait per runtime module: more traits in the busiest runtime files, and tools still needs the lifecycle types from below. (c) move `AgentDirectory` and all of `hub::types` down: it drags the overview, team events and the protocol into the runtime.

### D6. How agent↔tools↔background↔a2a breaks: one runtime crate or several

**Decided: (b), four crates, in this round.** The layering is agent (with subconscious) < background (with team) < a2a < tools: 273 of the 671 commits touch this code, and as one crate each such edit would rebuild 156k lines; as four, a tools edit (137 commits) rebuilds 57k and the critical path falls from 120k to 96k. The changes, each designed in §5:

- `Tool` and the `ToolRegistry` container move into `agent`; the registration methods become functions in `tools`, and the agent's two tool-reload methods move to their callers.
- background owns `SessionToolFactory`, the trait that builds each session's tool registry; tools implements it as `SessionTools`.
- `SpawnContext` loses the A2A handles (`a2a_hub`, `a2a_tracker`) and the lifecycle handle (`lifecycle`), and with them every other field only the session's tools read; the factory holds them.
- The agent's tests run on test tools in `agent::testing`.
- The agent's `TeamLink` sits behind an agent-owned trait, `TeamRoster`.
- `Interrupt` moves into the bus, beside the `MessageEvent` and `AgentMessageEvent` it wraps. No crate below the agent needs it (subconscious is a module of the agent's crate, and every other user is the agent or above), so the crate graph does not depend on this move; it keeps the interrupt vocabulary with the events it is made of.
- `diagnostics_dispatch` goes into `residuum-a2a`, the lowest crate below both of its users (tools and the hub's file routes) that can see every file kind it diagnoses; `client_context` goes back into `residuum-tracing-service`, where it lived until round 1 moved it to the root for its build-time variables (D8 removes those).
- The main/session registry parity in `src/tools/CLAUDE.md` stays enforced by the same test, which moves into tools with both registry builders, so every push that touches tools runs it.
- **Rejected.** (a) one `residuum-runtime` crate: no redesign now, but a 53k-line crate rebuilding 156k per edit, and a re-cut later that the "extract each crate once" rule avoids.
- **What follows.** The gateway keeps the main registry's injections (tools path, checkpoints, publisher) beside the agent, because the timezone and web-search reloads now re-register tools from outside the registry; the A2A server's end-to-end tests and seven team-file tests become cross-crate integration tests (D9); the main builder's test harness becomes a tools `test-support` item, because a gateway test keeps using it (§5).

### D7. Where `MessageOrigin`, `FileAttachment` and the other bus payload types go

**Decided: (a), into the bus crate, by topic module** (`bus::session`, `bus::origin`, `bus::attachment`, …), except `ExternalChannelConfig`/`ExternalChannelKind` and `teams::ENDPOINT`, which D12 places in config. The bus's events embed types from six modules above it (`src/bus/events.rs:12-13,230,256,323,435-493,743,801,805,844,910,1149,1151`; `src/bus/registry.rs:8-9,121-122`), every one data or a constant; the moved items are named in about 100 files, which change their imports mechanically.

- **Costs.** The bus stays the most expensive crate to edit (about 185k lines rebuild per edit, 68 commits in the window), which no option avoids, since the event vocabulary is what every producer and consumer shares; §11 lists it as a risk and §12 row 3d measures it.
- **Rejected.** (b) a payload crate under the bus: the bus and its payloads change together. (c) the event layer above the modules: checkpoints, workspace, notify and inference's `NoticeSink` impl publish on the bus from below.

### D8. Which crate embeds `web/dist`, which has the build script, and how the version reaches member crates

**Decided: assets (a), version (a).** The root keeps `#[derive(Embed)] #[folder = "web/dist/"]` (moved from `src/gateway/web/mod.rs:40-53` to `src/wiring.rs`, since the folder resolves against the deriving crate's manifest) and passes a getter to the hub in `HubInputs::assets`; the hub serves the web app through it and keeps it in `HubApiState` for the MCP catalog route (`/api/hub/mcp-catalog`). Only the root needs `web/dist`, and a web build rebuilds only the root. The root alone reads `RESIDUUM_VERSION` and `RESIDUUM_GIT_COMMIT`, into `pub const BUILD_INFO: residuum_core::BuildInfo`, and passes it down: `run_hub` takes it, `HubServices` carries it to each agent and its tools, and `client_context`'s and `update`'s functions take it as a parameter, as `workbench::SdkContext` already does. Member crates build and test without a web build and without anything that changes per commit.

- **What follows.** The getter's type is the hub's own (`WebAssetSource`, §5), since `rust_embed::EmbeddedFile` has no public constructor and hub tests must supply files without a build; the one asset test that checks the real build moves to the root.
- **Rejected.** For the assets, (b) the hub embedding `web/dist` with a build script of its own, so `cargo test -p residuum-hub` would need a web build, and (c) a `residuum-web-assets` crate, whose rebuild still rebuilds the hub. For the version, (b) a process-wide value set at startup (hidden dependency, unset in member tests) and (c) any member reading `env!` (rebuilds it and everything above on every commit).

### D9. What the pre-push hook tests, and where cross-crate integration tests live (with D11)

**Decided: one rule.**

- **Where the tests live.** A test lives in the crate whose code it tests and may use crates below it, through their `test-support` helpers. A test that needs a crate that is neither its own nor below it (a sibling, or a crate above) is a cross-crate integration test and lives in the root's `tests/it/`, as a module of the `it` binary. This round moves 155 such tests there: the hub's 136 real-agent tests (the host's 125 and the 11 that start the whole hub; they need the gateway's launcher), the A2A server end-to-end tests (11; they need tools' session tools), seven team-file tests that check write coordination between the hub's file API and agents' file tools (they need tools), and one overview test that compares the hub's schedule with the gateway's scheduled route. They wait in a root `#[cfg(test)]` module, `src/integration/`, while the crates are extracted, and move to `tests/it/` once the gateway is a crate (§10).
- **How each module says what it covers.** Each top-level module of `tests/it` declares the crates whose behavior it tests in one line of its module doc comment, `//! covers: residuum-hub, residuum-gateway`, naming packages (`residuum` for the root). The pre-push hook, through `scripts/affected-packages.sh`, and `scripts/ci-failures.sh` read it; a source-scan test checks every module has a valid one (§9).
- **What the hook runs.** For a push, the tests of the member crates the push touches (not their dependents), the root's unit tests for the root modules it touches (as today), and every `tests/it` module whose covers line names a touched package or whose own files changed. Clippy still covers the touched crates and every crate above them. Nothing above the touched crate runs beyond that; the merge queue's full suite covers it. There is no hand-coded entry for the hub: a hub push runs the real-agent tests because their module covers `residuum-hub`.
- **Costs.** 596 of the 671 commits touch a crate that has member crates above it; a failure in a dependent's tests now first shows in the merge queue, where it ejects the pull request and costs its batch a run. The `CLAUDE.md` advice to run dependents' tests by hand when a shared helper or trait changes still applies. A covers line that leaves out a crate the module tests makes that crate's pushes skip it, which the merge queue then catches. Every gateway push runs the 136 real-agent tests, because they test the gateway's launcher; §12 row 6b measures the cost.
- **What follows.** By `CONTRIBUTING.md`'s rule 7, the production items the moved tests call become plain `pub` and the test-only helpers `test-support` items; §6 lists the gateway's and the hub's. `unused_pub` counts a mention in `tests/it` as a use, so an item made `pub` for a test is reported once no test names it, if nothing else uses it; one its own crate's production code calls is never reported (§6). Before each crate is extracted its covers name is resolved through a temporary path table (§9).
- **Rejected.** Running every member above the touched crate (today's rule): a bus or workspace push would run nearly the whole suite. Keeping the real-agent tests in the gateway crate (D11 (a)): they would run on gateway pushes only, never on hub pushes, unless a hand-kept hook entry added them.

### D10. How granular to go overall

**Decided: (b), a crate per domain: thirteen, with the runtime in four (D6).** The lower four (workspace, checkpoints, notify, proactivity) are separate because each is its own domain with its own heavy dependencies (gix in checkpoints, the macOS and Windows notification crates in notify), they test alone, and they log under their own names. Each crate costs a manifest, a test binary, a `rustdoc --test` pass, three isolation checks in the merge queue, a line in the hub.md crate list and an entry in the docs.

- **Rejected.** (a) one services crate for the lower four: 102k on the critical path against 96k, for three manifests fewer. Finer still (the adapters as crates, D4 (b)): 2k, which waits for a measurement (D4).

### D11. Where the hub-plus-gateway integration tests live

**Decided: (b), in `tests/it/`, under D9's general rule**, which covers every cross-crate integration test, not only the hub's; the hook runs them through their covers lines rather than a fixed hub entry.

### D12. Five small items whose obvious home is core or config

**Decided: process (a), channel types (a), `last_known_good` and `FilterReload` (b).** `src/process.rs` (used by pulse, tools and the Teams setup; 2 commits in the window) moves into `residuum-core`, with `nix` in core's `cfg(unix)` table and `tokio-util`; the parsed `channels.toml` types `ExternalChannelConfig`/`ExternalChannelKind` (`src/notify/types.rs`, used by the bus registry) move into config as `channels`, and `teams::ENDPOINT` beside `WEB_UI_ENDPOINT`; `gateway::last_known_good` (used by the hub, the gateway and the CLI; 6 commits) and the `FilterReload` trait (`src/logging/mod.rs`, which the hub calls) move into the hub, their lowest user, where an edit rebuilds about 87k lines instead of 259k. Target-specific dependencies then follow one rule: declared once in `[workspace.dependencies]` and named `{ workspace = true }` in the target table of each crate whose code uses them (§8).

- **Rejected.** process into proactivity (its lowest user, not by name) or a crate of its own; the channel types into the bus (rebuilds 185k instead of 259k, a dozen commits a month between all five items); `last_known_good` and `FilterReload` into config.

### D13. Smaller layout choices

**Decided as listed**, each with its reason:

- **The inbox and the inbound attachment code join `residuum-workspace`** rather than a crate of their own. Both depend only on the bus, inference and config, and their dependents are workspace's too, so a separate crate rebuilds the same set and adds a manifest.
- **The A2A listener and its test double stay with the A2A code, in `residuum-a2a`.** `StaticAgentDirectory` (`src/a2a/static_directory.rs`, test-only today) implements `TeamDirectory` and stays beside `listener_tests.rs`; the hub's tests that used it as a full directory get a hub-side wrapper (§5). Moving the listener and its tests into the hub would make many a2a items `pub` for one test file.
- **Two renames ride with the moves:** `GatewayExit` becomes `HubExit` (the hub returns it), and the session stop check becomes `background::registry::stop_named_session`. No user sees either.

### Why each boundary is where it is

- **The bus carries data only.** Every type it embeds is data or a constant (§5), so moving them down cuts every bus edge into the root without a trait. `Interrupt` is one more such type.
- **workspace carries the inbox.** The inbox's only upward edge is the attachment type, and the attachment code is the inbox's inbound side; together they depend only on the bus.
- **proactivity needs nothing above the bus.** pulse's production code uses only the bus (once the address helpers move there) and `process` (in core); its one workspace use is a test (`src/pulse/types.rs:1128`), so workspace is only its dev-dependency.
- **protocol is beside the runtime.** Once the payloads are in the bus, the protocol names no runtime type, so a protocol change rebuilds only the hub, the gateway and the root.
- **The runtime is a chain.** subconscious names only the bus once `Interrupt` is there; the agent names subconscious (`SubconsciousWatch`, `src/agent/core.rs:381`) and nothing above it once tools' container is its own; background runs turns through the agent; a2a delivers through the background messenger; tools calls all three. - **The hub sits on a2a, beside tools.** The hub starts the A2A listener (`src/hub/runtime.rs:282`) and reads the A2A keys, sibling fan-out and open tasks, but names no tool in production; its tests that drive agent tools are integration tests (§7). So a tools edit does not rebuild the hub.
- **The hub sits on interfaces for the Teams setup alone.** Its Teams setup routes call the setup job in `interfaces::teams` (D14); nothing else in the hub names an interfaces item, and the adapters are the gateway's to build.
- **The A2A listener stays in a2a** (D13). It needs `summary` and `agent_a2a_router` only, which `TeamDirectory` gives.
- **daemon and logging stay in the root.** The hub uses one function of each (`daemon::write_ready_file`, `src/hub/runtime.rs:513`; `logging::global_filter_handle`, `:815`); `run_hub` takes them as inputs, and the CLI, their main user, keeps them.

## 6. Visibility and API policy

Round 1's policy applies as it stands in `CONTRIBUTING.md` ("Public API", "The root facade"), including the five-step rule for each item the compiler reports as private to the crate that needs it, and each extraction's pull request lists every item it made `pub` with its kind, the step that applied and its callers outside the crate. What round 2 adds:

- **`unused_pub` starts to apply.** `testing::source_scan::unused_pub` checks only member crates (`src/testing/source_scan/unused_pub.rs:106-113`), so every `pub` item of the code that moves becomes a candidate: an item named nowhere in the workspace outside its own declaration, its own crate's `#[cfg(test)]` code and its own `use` lines fails the scan. Each extraction runs the scan and, for each report, deletes the item, narrows it to `pub(crate)`, or moves a test-only helper into `#[cfg(test)]` code. A use in the crate's own production code counts, so this reports only dead or test-only items.
- **Existing `pub` stays `pub`** (rule 5) where `commands/`, `tests/it` or `tests/ts_export.rs` use it. Items that are `pub` today with no user outside their crate are what `unused_pub` reports and get narrowed.

**Stopping between chunks.** Every chunk leaves `main` working, so the work can pause after any of them, and each can be reverted on its own. After the P and R chunks the root is still one crate, with its internal graph acyclic; the X chunks then only move files, and I1 only moves tests.

## 11. Risks, and what to do when something regresses

Round 1's regression table (`docs/archive/workspace-split.md` §13) still applies; these are the ones round 2 adds or makes likelier.

| regression | what would be seen | what catches it |
|---|---|---|
| A test is lost when tests change crate or module (R2, R6, P12, P14, I1, the upward tests) | fewer tests, all green | the test-count check of every chunk |
| An agent's start, stop or crash recovery behaves differently through the launcher | an agent that doesn't start, restart, or report its failure | the host integration tests, unchanged in substance; P11 lands while they still run in place |
| A session gets different tools from main, or loses one, through the factory (R3) | a session that cannot do what main can, or can do what it should not | the parity test, which after R4 runs on every tools push; the session tests in background and the A2A server tests |
| A tool registers in a different order or under different gating after R1 | a missing or extra tool, a changed tool list in the model's prompt | the parity test and the registry tests, unchanged in their assertions |
| The bus stays the most expensive crate to edit (D7): 68 commits in the window, each rebuilding about 185k lines, now as a chain of thirteen crates whose per-crate overhead the model does not count | a bus edit slower than today's single-crate rebuild | §12 row 3d; a miss is investigated from the `--timings` report, not redesigned in this round |
| The version shown is wrong | hub status, the web UI's version, the workbench SDK or a bug report disagrees with the binary | the version tests, which assert the `BuildInfo` passed in comes back out; P9's grep that only `src/lib.rs` reads the variables |
| A member reads the version variables later | `env!` fails to compile there (the variable is set only for the root); `option_env!("RESIDUUM_GIT_COMMIT")` would compile and send bug reports without a commit | the compiler for `env!`; P9's source-scan rule for both |
| The web app is missing or stale | a blank page or an old UI | the root's assets tests (moved from `assets.rs`), which read the real build; `build.rs` still asserts `web/dist` |
| A route lands in the wrong half of the web split (P12) | a repair or file route that 404s for a stopped agent, or a running-agent route the hub serves | the hub HTTP tests of the repair and file routes in every agent state, which stay in the hub with their assertions unchanged |
| A log line moves to a target nobody filters on | `RUST_LOG=residuum::hub=trace` has no effect | not detected; documented in hub.md's crate list and `CLAUDE.md` (each X chunk, F1) |
| `is_hub_level` misses the hub's new prefix | the host test fails, reporting hub lines without an agent | the test itself (X12 updates it) |
| Interfaces edits get slower (D14) | an adapter change rebuilds the hub too, about 103k lines instead of the adapters' own 51k | §12 row 3e; D14 (c) is the split if it misses |
| A Teams or `/stop` message changes wording | a user sees a different message | the existing message tests, which P5a and P5b keep unchanged |
| Pre-push no longer runs a dependent's tests (D9) | a broken dependent passes pre-push and the pull request lane (which runs only the Windows clippy for Rust); the merge queue's full suite fails it, ejects the pull request and costs its batch a run | the merge queue; the hook prints what it chose; the cross-crate tests run on pushes to any crate they cover |
| A `tests/it` module's covers line leaves out a crate it tests | that crate's pushes skip the module; the merge queue fails it | review of the line; `ci-failures` marks such a failure untouched, which points at the line; the scan checks only that names are valid |
| Between P14 and I1 the cross-crate tests are root unit tests | they run as `integration::<m>::` filters, selected by the same covers lines | T3's `integration` arm, removed by I1 |
| Gateway pushes get slower | the hook runs the 136 real-agent tests on every gateway push, since their modules cover the gateway | §12 row 6b |
| The test run gets slower | `cargo test` takes longer although builds are faster | row 7; libtest runs each crate's binary in turn, so thirteen more binaries add their slowest tests in series. If it misses its target, measure where the time goes before changing the runner |
| A dev-dependency cycle sneaks in through a test helper | a crate compiled twice in tests, types that stop unifying | `manifest_scan` rule 5 |
| A crate builds only because another turns on a feature | `cargo test -p residuum-<x>` fails for a developer though CI was green | the merge queue's isolation job |

**Recovery.** Any chunk is reverted by a revert pull request of its merge commit. A P or R chunk's revert restores the old module path in one place; an X chunk's revert puts the files back in the root without touching the other crates. Measurements are taken at M0 and F2, and an orchestrator can measure between X chunks to decide whether to continue.

## 13. What round 2 leaves in place

- **The bus stays expensive to edit.** Every crate above it depends on its event vocabulary, so each of its commits rebuilds about 185k lines; no layout changes that. Row 3d measures what the chain of crates costs on top.
- **The hub is the largest and among the most edited crates** (47k lines, 205 commits in the window), because D2 moved the hot web code into it; each edit rebuilds about 87k lines. The web code is the hub's to split further if §12 shows the cost.
- **The chat adapters stay in one crate, with the Teams app setup** (D4, D14), and the hub depends on it, so every adapter edit rebuilds the hub (about 103k lines, row 3e). Teams is the candidate to split first: as a crate of its own it would be the hub's only adapter dependency, so Discord and Telegram edits would stop rebuilding the hub (D4 (b)); D14 (c) takes out only the setup and takes the hub off the adapters entirely.
- **Two `A2aVisibility` enums** remain, one in `residuum_config` (the parsed setting, `crates/config/src/types.rs:253`) and one in the lifecycle types (the API form, moving to `background::team`); round 2 moves the second and does not merge them.
- **The root keeps `daemon`, `logging` and `setup_wizard`**, which only the CLI and the wiring use.
- **No check ties the hub's dispatch lists to its route tables** (`src/hub/http/dispatch.rs:49-90` names the repair and file prefixes by hand); after P13 both are in the hub crate, but nothing tests that they agree.
- **A production item made `pub` for a test can outlive it.** `unused_pub` never reports an item its own crate's production code calls, so such an item (§6) stays `pub` after its last test goes unless that pull request narrows it.
